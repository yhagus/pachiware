# API Reference

Base URL lokal: `http://localhost:3001`.

## API Keys and Tenants

API keys are global. A key may act only on tenants created under it; a tenant's `apiKeyId` is `null` when it is not under any key (for example, created from the console without choosing one).

```bash
# Create a key (raw value is returned once):
curl -X POST http://localhost:3001/api/admin/api-keys \
  -H "X-Platform-Key: $PLATFORM_ADMIN_KEY" -H 'Content-Type: application/json' \
  -d '{"name":"Production"}'

# Create a tenant under that key:
curl -X POST http://localhost:3001/api/v1/tenants \
  -H "Authorization: Bearer $PACHIWARE_API_KEY" -H 'Content-Type: application/json' \
  -d '{"name":"Example Team","slug":"example"}'

# Act on it (tenant id or slug in X-Tenant-Id):
curl http://localhost:3001/api/v1/tasks \
  -H "Authorization: Bearer $PACHIWARE_API_KEY" -H "X-Tenant-Id: example"
```

The issue response contains `{success, raw, keyPrefix, keyId}`. `raw` is returned once; key-list endpoints expose metadata and prefixes only. Keys currently get scope `*` (full access); the middleware already enforces `resource:read` / `resource:write` scopes for when custom scopes are added.

## API Contract

`GET /api/health` is public: readiness, data-store health, and an array of active bot runtime statuses. A database with no tenants reports `setupRequired: true`.

All `/api/admin/*` requests require `X-Platform-Key`. JSON mutations require `Content-Type: application/json`.

Usage ranges accept ISO dates, including both boundaries. Invalid or reversed ranges return 400. Each aggregate row carries `events`, `promptTokens`, `completionTokens`, and `cachedTokens` (the prompt tokens the provider served from its cache). Events include `llm_tokens` (successful completions with prompt/completion token counts; `metadata` holds `cachedTokens`, `latencyMs`, the provider's response time in milliseconds, and `profileId`, the profile that answered, when the bot has one), `tool_call` (tool name/success), and `discord_message` (accepted inbound requests). Guardrail audit events (`guardrail_denied`, `tool_denied`, `confirmation_requested`, `confirmation_accepted`, `prompt_injection_detected` and the `thread_confirmation_*` ones) and `model_fallback` (`metadata` `{profileId, from, to, models}`: the bot's profile, its first model, the fallback model that answered, and how many models were asked; rows from before fallback models are `profile_fallback`, `{from, to, profiles}` with profile ids) count here by type; their `metadata` holds categories and ids only. `confirmation_requested` holds `{tool, effect, confirmationId}`; rows written before effects replaced risk levels hold `risk` (`read`, `write` or `destructive`) instead of `effect`. Bot deletion retains a disabled tombstone to preserve historical usage/conversation references and erases its token.

All `/api/v1/*` requests require `Authorization: Bearer <API key>`. Except `/api/v1/tenants`, they also require `X-Tenant-Id` (id or slug): missing header returns 400, a tenant that does not exist or is not under the key returns 404. Missing/revoked keys return 401; suspended tenants and insufficient scopes return 403.

**Availability rules.** A rule turns something off at one level: the tenant, a bot, a guild of that bot, or a channel of that guild. A level without a rule inherits what the level above allows, so a tenant with no rules is offered every tool of its enabled skills. A tool is offered, and runs, only when its skill, the tool itself, and its effect are available at the place the message came from; a thread uses its parent channel. An effect rule (`name` is `read`, `write` or `danger`) covers every tool with that effect, including multi-action tools, playbook tools and tools added later; a tool whose effect is off stays off whatever its own rules say below. A playbook starts only where the playbook and every skill it requires are available; the tools that serve it are available exactly where it is (and its effect allows them), and a thread bound to it ends with a short note on its next message once it is not. `GET` returns `{rules, inherited}` of that level. `rules` are the level's own, each `{kind, name, value}`. `inherited` is what the levels above leave it: one `{kind, name, available, off?, optIn?}` per target that a level above has a rule on, plus each skill the tenant switch turned off (as `off: "tenant"`). `available` is whether the target reaches this level, `off` names the highest level above that turns it off, and `optIn` the lowest level above that made it opt-in (with `available: false` and no `off`, it waits for an `on` here or below). A target not listed is available from above; the tenant level inherits nothing. `PUT {kind, name, value}` sets one rule and `DELETE ?kind=&name=` clears one (the target then follows `inherited` again); both return the level's `{rules, inherited}`. `kind` is `playbook`, `skill`, `tool` or `effect`, `value` is `off`, `opt_in` or `on`. `opt_in` (bot or guild only) keeps the target available at that level but off at each level below until one says `on`, so a guild opt-in reaches only the channels that say `on`, and a channel seen later does not get it. `on` (guild or channel only) answers an `opt_in` on the same target at a level above. A rule cannot turn back on what is off above: 400 for an `opt_in` or `on` on a target that a level above turns off, and for a tool also when its skill or its effect is off above; an `off` written above later still wins over an `on` below. Writing the same target twice replaces its value. A guild's and a channel's `GET` also return `guildPlaybooks`: the playbooks that server made in chat, as the workspace route lists them, without those a tenant or built-in playbook hides. They take rules only at that guild and its channels; a tenant or bot rule naming one is an unknown playbook. 400 with `{error}` for `on` without an `opt_in` above, `opt_in` at the tenant or a channel, `on` at the tenant or a bot, an unknown playbook (built-in, the tenant's own, or at a guild or a channel that server's own), skill, tool or effect, a tool that serves a playbook (it follows its playbook), or a skill rule at the tenant level (use the skill switch). Deleting a bot removes its rules.

Credential config fields are `openaiApiKeyEncrypted`, `anthropicApiKeyEncrypted`, and `customApiKeyEncrypted`. On writes these accept **plaintext** and encrypt server-side; reads return `••••••••` or null. Omitted/masked values preserve the existing key; null or empty clears it. Bot responses expose `hasToken` rather than a token. Old unauthenticated `/api/agent/*`, `/api/tasks`, and `/api/skills` endpoints are removed.

| GET | `/api/admin/bots/:botId/guilds/:guildId/config` | `{systemPrompt, useThreads, alwaysChannelIds, timezone, language, digestChannels, dailyLogChannels, docSources}`; defaults when unset (`timezone` and `language` null mean the tenant's) |
| PUT | `/api/admin/bots/:botId/guilds/:guildId/config` | Partial update. `systemPrompt` ≤ 8000 chars (empty clears), `useThreads` boolean, `alwaysChannelIds` string[] (max 50), `timezone` IANA name or null, `language` `id`, `en` or null, `digestChannels` `[{channelId, hour}]` (hour 0 to 23, one entry per channel, max 50). Saving keeps one daily `digest` schedule row per entry in the guild's zone and cancels the rows of entries removed. `docSources` `[{channelId, repo, account?, paths}]` (max 50, one entry per channel and repository; see below) |

**Doc sources.** Each entry mirrors the documentation of one repository into one channel's Workspace folder, at `files/docs/<owner>/<repo>/<path>`, where it is a Document that `searchFiles` and `recall` find like any kept file. `repo` is `owner/name` (a GitLab subgroup path too), stored lowercase. `account` names one of the bot's git accounts; left out, the first account the channel's Git scope allows the repository for reads it. `paths` holds 1 to 20 patterns over repository paths: folder and file names, `*` within a name, `**` across folders (`README.md`, `docs/**`, `adr/*.md`); a leading `/`, `.` or `..`, and other glob syntax are refused. Only `.md`, `.mdx`, `.markdown`, `.txt`, `.rst` and `.adoc` files on the default branch are copied, at most 200 per source, taken in the order of the patterns and then by path; a file over 256 KB, or whose path is too deep or holds a name the Workspace refuses, is skipped. 400 with `{error}` when a new or changed entry names a repository its channel's Git scope does not allow (for the named account, when given); an entry saved before stays when the scope narrows later. Saving a new or changed entry mirrors it at once in the background; a daily `docs-mirror` schedule row per channel with entries refreshes them at 00:30 in the guild's zone, with the Daily logs. A refresh reads only what changed since the last one: nothing past the head commit when it and the patterns are unchanged, otherwise only the blobs whose sha changed; each file written gets a keyword head, and a file no longer matched upstream (deleted, or renamed out of the patterns) is deleted. A hidden `.mirror.json` beside the files records the commit, each file's blob sha and what was skipped. A source its channel's Git scope no longer allows is skipped and its files kept, with one `docs_mirror_not_allowed` audit row; a refresh that fails leaves a `docs_mirror_failed` audit row and stops nothing else. Removing an entry deletes the files its mirror holds.

`systemPrompt` is appended to the tenant prompt under "Server instructions" for that server only. The bot answers DMs, its own threads, `alwaysChannelIds` channels, and @mentions or replies to it. With `useThreads`, a mention opens a thread and the conversation continues there without mentions. Guild conversations are shared per channel or thread, and turns are prefixed with the speaker's name.
