# Triage

Move the issues of this thread's repository through a small state machine of triage roles.

Only the person who started this thread decides: they are the maintainer here. Others give input.

Every comment or issue you post during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference files

Read them with `readPlaybookFile` when you need them:

- `triage/AGENT-BRIEF.md`: how to write durable agent briefs
- `triage/OUT-OF-SCOPE.md`: how the `.out-of-scope/` knowledge base works

## The repository and its labels

Call `playbookRepositories` first, unless the prompt already names this thread's repository. With several allowed, ask the person which one, in one line, and wait.

Then call `repoLabels` and map each role below to the repository's label for it: the same name, or the obvious equivalent (`type: bug` for `bug`). When a role has no label, ask the person once which label stands for it, or whether to go without it; never invent a label.

## Roles

Two **category** roles:

- `bug`: something is broken
- `enhancement`: new feature or improvement

Five **state** roles:

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `ready-for-agent`: fully specified, ready for an AFK agent
- `ready-for-human`: needs human implementation
- `wontfix`: will not be actioned

Every triaged issue should carry exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before doing anything else.

State transitions: an unlabeled issue normally goes to `needs-triage` first; from there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. The maintainer can override at any time; flag transitions that look unusual and ask before going on.

Triage covers issues. A pull request the maintainer names is triaged the same way, as an issue with attached code: read its diff with `repoMergeRequestDiff`, and set its labels with `repoSetLabels` (kind `pr`), since the batch below takes issues only.

## Invocation

The maintainer starts this playbook and describes what they want in plain words. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42"
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Writes and confirmation

Every write waits for the maintainer to press Confirm, and after Confirm you get no further turn: the result shows on the confirmation message. So make at most one write per reply and wait for the maintainer to come back before the next.

Put every label and state change you make at once into **one** `repoUpdateIssues` call, so the maintainer presses Confirm once for the whole set: moving three issues to `ready-for-agent` and closing a fourth as `wontfix` is one batch. `labels` there **replaces** an issue's labels, so give each issue its full new list: keep the labels that are not triage roles, and swap the old role for the new one. Read the current labels from `repoIssues` or `repoIssue` first. A batch holds at most 25 issues.

## Show what needs attention

Query the repository and present three buckets, oldest first:

1. **Unlabeled**: never triaged. Open issues from `repoIssues` with no labels.
2. **`needs-triage`**: evaluation in progress. `repoIssues` with that label.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation. `repoIssues` with that label, then `repoComments` on each.

Show counts and a one-line summary per item, under 1,800 characters. Let the maintainer pick.

## Triage a specific issue

1. **Gather context.** Read the full issue with `repoIssue` and `repoComments` (body, comments, labels, author). Parse any prior triage notes so you do not ask again what was resolved. Explore the code with `repoSearchCode` and `repoReadFile`, using the vocabulary of the repository's `GLOSSARY.md` and respecting the decision records in `docs/adr/` in the area. Run two checks: (a) **redundancy**: search for an existing implementation of the requested behaviour by domain concept (not just the request's wording), and report where you looked. If found, it is an already-implemented `wontfix` (step 5). (b) **prior rejection**: read the files in `.out-of-scope/` with `repoReadFile` and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief summary of the code relevant to the request (including whether it is already implemented). Wait for direction.

3. **Check the claim.** Before any grilling, check whether the claim holds up as far as you can without running anything: you cannot check out code or run tests. For a bug, follow the reporter's steps through the code and say what the code reads as; when CI is involved, read it with `repoChecks` and `repoJobLog`. For a pull request, confirm from the diff that it does what it claims. Report one of: the code path that confirms it, the code path that contradicts it, or insufficient detail (a strong `needs-info` signal). Say plainly that it was read, not reproduced.

4. **Grill (if needed).** If the request needs fleshing out, follow the loaded `grilling` and `domain-modeling` playbooks and grill it into shape a round of questions at a time, sharpening domain terms and writing the glossary and decision records with `writePlaybookDocument` as decisions land.

5. **Apply the outcome**, one write per reply:
   - `ready-for-agent`: post an agent brief comment with `repoComment` (`triage/AGENT-BRIEF.md`).
   - `ready-for-human`: the same structure as an agent brief, but note why it cannot be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`: post triage notes with `repoComment` (template below).
   - For `wontfix`, the comment depends on _why_, and the issue is closed in the batch:
     - **Already implemented**: point to where the change lives; do **not** write to `.out-of-scope/` (that is for _rejected_ requests, not built ones).
     - **Rejected (bug)**: give a polite explanation.
     - **Rejected (enhancement)**: write the `.out-of-scope/` file (`triage/OUT-OF-SCOPE.md`) on a new branch with `repoWriteFile`, open a pull request for it with `repoOpenPullRequest`, and link it from the comment.
   - `needs-triage`: apply the role. Optional comment if there is partial progress.

   The role change itself, and closing a `wontfix`, go into the `repoUpdateIssues` batch, together with every other issue triaged in this thread so far whose labels are not set yet.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust them and apply the role directly. Say what you are about to do (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without grilling it first, ask whether they want an agent brief written. When they move several issues at once ("move #42, #43 and #47 to ready-for-agent"), it is one `repoUpdateIssues` batch.

## Needs-info template

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work is not lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous triage

If prior triage notes exist on the issue, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before going on. Do not ask again what was resolved.
