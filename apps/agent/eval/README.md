# Live evals

This folder holds two evals that compare profiles on the same work, graded the same way: the **issue-draft eval** (how well the issue-draft playbook turns a brief into drafts) and the **daily-behaviour eval** (everyday assistant work: tasks from casual wording, relative due dates, status changes, remember and forget, file search, Reminder creation, and project work: assignees, Progress notes, cancelling, ambiguous references, and a person's tasks across channels, and questions about kept Minutes, Decisions, Notes and Documents across channels). The decisions behind the first are in issue #28; the research is `docs/research/evaluating-issue-drafts.md` on the `research/evaluating-issue-drafts` branch. The second follows spec #72, block 8, spec #120 for project work, and spec #146 for kept material.

Two halves, for both:

- **Code checks** run on every `bun test` over the recorded outputs in `recorded/` (`apps/agent/test/eval-*.test.ts`). The judge, comparison and report code is tested there too, with a scripted model and a scripted judge. None of these tests need a key.
- **The live eval** (`drafts.eval.ts`, `assistant.eval.ts`) runs only on demand. It drives the real bot through the Discord scenario harness with real profiles; the issue-draft eval runs against this repository at the commit pinned in `repository.yaml`, served offline, and the daily-behaviour eval against a fixed clock. A pinned judge grades every trial. Neither gates CI.

## Running a live eval

```sh
EVAL_LIVE=1 \
EVAL_PROFILES=apps/agent/eval/profiles.yaml \
EVAL_JUDGE_PROVIDER=anthropic EVAL_JUDGE_MODEL=<judge model> EVAL_JUDGE_API_KEY=<key> \
bun run eval              # issue drafts
bun run eval:assistant    # daily behaviours
```

| Variable | Meaning |
|---|---|
| `EVAL_LIVE=1` | Without it the file only reports a skipped test. |
| `EVAL_PROFILES` | Path to the profiles to compare. Copy `profiles.example.yaml` to `profiles.yaml` (gitignored). Each profile names the env variable holding its key (`apiKeyEnv`), and may give `acceptsImages` and a `price` in USD per million tokens: `{ input, output, cachedInput }`, `cachedInput` (optional) for prompt tokens the provider served from its prompt cache. |
| `EVAL_PROVIDER`, `EVAL_MODEL`, `EVAL_API_KEY`, `EVAL_BASE_URL`, `EVAL_ACCEPTS_IMAGES=1` | One profile, used when `EVAL_PROFILES` is unset. |
| `EVAL_JUDGE_PROVIDER`, `EVAL_JUDGE_MODEL`, `EVAL_JUDGE_API_KEY`, `EVAL_JUDGE_BASE_URL` | The judge: `openai` (default), `anthropic`, or `custom` with a base URL. Model and key are required. `offline` needs neither: see "Judging offline". |
| `EVAL_TRIALS` | Trials per brief and profile, default 3. |
| `EVAL_EXAM` | Daily behaviours only. `1`: run the Rapor's exam (`scorecard.yaml` `briefs`), not every brief. `lived-in`: run the lived-in exam's sessions (`lived-in/sessions/`) against `lived-in/scorecard.yaml` instead; see "The lived-in exam". |

The run refuses to start when the judge's model is any compared profile's model (a vendor prefix such as `anthropic/` is ignored when comparing). A model grades its own output too kindly, so keep the judge outside the comparison.

Each trial runs in its own subprocess. Results land in `results/<run>/` (`results/assistant-<run>/` for the daily-behaviour eval): one JSON per trial under `trials/`, then `report.json` and `report.md` once every trial is done. Both reports record the judge's provider and model, the rubric version, the number of trials, and, for issue drafts, the pinned commit; a lived-in run records `exam: lived-in`, so `rejudge.ts` and `offline-judge.ts` find its sessions and scorecard again. `report.md` ends with cost and latency per profile and per trial, and, when the briefs name gold sources, a Retrieval section (see "How profiles are compared"). Failed trials are never retried; a retry would hide exactly the variance the trials measure.

### Judging offline

Without a judge API, run the daily-behaviour eval with `EVAL_JUDGE_PROVIDER=offline`: no judge is called, every trial is recorded with its code checks, and each test fails only on those. Then:

1. `bun apps/agent/eval/offline-judge.ts prompts apps/agent/eval/results/<run>` writes `judge-prompts.jsonl`: every question the HTTP judge would get, word for word, each once, except those that cannot change a verdict (the questions of a turn its code checks failed, and every question of a trial whose every turn they failed).
2. Answer each line as the judge would, from a model outside the compared profiles (another vendor), or by hand: one `{"id", "reasoning", "verdict"}` a line, verdict `yes`, `no` or `unknown`.
3. `bun apps/agent/eval/offline-judge.ts grade apps/agent/eval/results/<run> <answers.jsonl> <provider> <model>` refuses answers that leave a question out, then regrades the run into `rejudged-<rubric>/` with the Rapor, naming the judge as given. A question not written grades unknown, so the question rate counts it as not answered.

## How a draft is graded

Cheapest layer first:

1. **Code checks** (`checks.ts`): the draft checker's limits (title, acceptance criteria, open questions, body size), proposed labels exist in the repository, every Context used link resolves at the pinned commit, no stock filler, and the draft is in the brief's language.
2. **Judge** (`judge.ts`), one isolated call per criterion. The judge sees the brief, the author's answers and the fixture's reference facts, reasons first, and ends with `yes`, `no` or `unknown`:
   - per must-cover fact: do the brief's drafts, taken together, cover it?
   - per question the bot asked (round questions and the drafts' own open questions): does it probe a known gap or a real ambiguity?
   - per draft: is every statement about the repository supported by the allowed repository facts, the brief, the answers, or the files under Context used?

A draft **passes** when it passes every code check, the brief's drafts cover at least 80% of the must-cover facts, and the judge does not answer `no` on the draft's repository statements. `unknown` never counts as covered, and an `unknown` on repository statements does not fail a draft. Question quality is reported as a rate, not a gate. A judge call that errors counts as `unknown`, with the error as its reasoning.

## How a daily-behaviour turn is graded

A daily-behaviour brief is a short conversation: the brief, then follow-ups in the thread the bot opened. After every turn the runner (`assistantRun.ts`) records the bot's replies and the state a person could see: the channel's tasks (title, status, due date, assignee, creator, Progress notes), plus those of any other channel the brief seeded tasks in, marked with that channel, the channel's and the server's Memory lines, the files under `files/`, the Reminder rows, and the text of each Minutes and Daily log the bot wrote in the channel (the seeded ones aside). A turn another member spoke records who (`authors`), and a run that seeded talk records each seeded message's link (`seeded`). The grade is per turn, so a trial's score is the share of its turns that pass, in place of the share of drafts.

1. **Code checks** (`assistantChecks.ts`), against the `turns` entry of `facts.yaml` for that turn: the bot replied, or, on a `quiet` turn, posted nothing; it left one of the `reaction` emoji when the facts name some; no Confirm button was offered (task writes, Memory and Reminders need none); nothing was pinged (only a Reminder post pings); an ambiguous turn left the Workspace as it was; the tasks match (each expected task is found by a phrase of its title, then status, `dueAt`, assignee, creator and channel are compared when given, `notes` phrases must each be in a Progress note (an empty list means none), and the count must agree; `tasksInclude` checks its tasks the same way among any others, without the count, for a brief seeded with dozens of tasks); Memory has and lacks the given lines; `files/` holds exactly the given files; the Reminder rows match (recurrence, weekdays, time of day, `nextAt`, mentions); each `kept` phrase is in a Minutes or Daily log the bot wrote; the reply links each seeded message `cites` names; the reply mentions or avoids given phrases, and lists tasks in the fixed `status | due | assignee | id | title` format when the facts say it does; no stock filler; no reply reads as the other language; and no reply leaves a ref such as `[K1]` unrendered or links anything the seed does not hold (its files' text, a seeded Minutes' posted message, a seeded pull request, issue or commit, a seeded message). When `then` names a clock, the scheduler ticks once at it and the Reminder posts are checked for their text and pings, charged to the last turn.
2. **Judge** (`assistantJudge.ts`), the same pinned judge with its own rubric (`ASSISTANT_RUBRIC_VERSION`), one isolated call per criterion, with the conversation and the recorded state in front of it:
   - per must-cover fact: do the replies, taken together, convey it?
   - per turn: on a clear request, did the bot act without asking back; on an ambiguous one (the fixture says what is unclear), did it ask exactly one question that names the gap and refrain from acting?
   - per turn: is every statement about tasks, Memory, files or Reminders supported by the recorded state, the reference facts, or the conversation?

A turn **passes** when it passes every code check, the brief's replies convey at least 80% of the must-cover facts, and the judge answers neither `no` on the act-or-ask question nor `no` on support. `unknown` never counts as conveyed and never fails a turn. The share of turns where the bot acted or asked as called for is reported in the question-rate column. A trial passes when every turn passes.

## How profiles are compared

Every profile runs the same briefs. A trial scores the share of its drafts (or turns) that pass (0 when no draft was posted). Trials are averaged per brief, and the profile's score is the mean over briefs.

- **Paired differences**: for each pair of profiles, the mean of the per-brief score differences, with the standard error of that mean. Pairing removes how hard each brief is. At about 20 briefs only large differences stand out; treat anything within two standard errors of zero as noise. The daily-behaviour set is smaller still, so read its differences as a hint.
- **pass^k**: the share of briefs where every trial passed, the reliability a user feels.
- **Cost**: tokens per run from the usage events, priced when the profile has a `price`. The Cost and latency section of `report.md` gives, per profile and then per trial, the prompt tokens (those served from the provider's prompt cache in brackets), the completion tokens, the model calls, the summed model latency, the wall time and the cost. Cached tokens are priced at `cachedInput` (at `input` when it is left out); for OpenAI-style providers they come off the prompt count, which includes them, while Anthropic reports them beside it.
- **Latency**: the router records `latencyMs` on every model call's usage event; the report shows the mean per call, plus the wall time per run, and the totals above.
- **Retrieval**: when a brief's turns name `gold` sources (the lived-in sessions do), the runner records what each turn's searches showed (recall, searchFiles, listTasks, repoSearchWork, part by part as the model saw them) and `retrieval.ts` scores it with no judge: recall@5, the share of a turn's gold sources found among the first 5 of their part (kept files, Tasks, git work), and the reciprocal rank of the first one within 10. A trial averages its turns with gold, a brief its trials, a profile its briefs with gold; the Retrieval section of `report.md` has both, per profile and per brief. A turn that names gold and searched nothing scores 0.

## The Rapor

The Rapor is the harness score (spec #226): the daily-behaviour eval run live against the model the tenants use, scored per area and as one weighted number out of 100. `scorecard.yaml` holds the exam:

- `version`: bumped on any change to the weights, the briefs or the holdouts; only reports at one version compare.
- `weights`: capture 20 (Minutes, Daily logs, Documents), recall 25, tasks 20 (Tasks, Reminders and project work), group 10 (several people at once), loop 15 (the agent loop itself: Memory, tool use, links). The other 10 of the review's rubric, the eval itself, is met by how the run is made, not by briefs.
- `briefs`: the exam, each a folder under `assistant/` whose `facts.yaml` names its `area`. Version 2 (#239) has 30, 22 of them in Indonesian, the language the tenants' teams speak, and at least 4 in each area. The other briefs under `assistant/` keep their dry runs and recordings and run live, but the Rapor does not count them.
- `holdout`: the briefs among `briefs` that are held out, drawn per version, not chosen (#252). `{ draw: 6, seed: rapor }` holds out six: of the briefs not `spent`, the best-ranked of each area in turn, then the best-ranked of the rest, ranked by a sha256 of the seed, the version and the brief's name (`drawHoldout` in `scorecard.ts`). Every bump of `version` draws a new set that nobody picked, so a fix tuned against one version's holdouts meets others at the next. `spent` lists briefs used to tune while they were held out; no draw picks them again. `fixed` pins the set of a version from before draws: version 3 keeps the six chosen by hand, `notulen-pemilik-tenggat`, `holdout-parafrasa-volume`, `keputusan-bertentangan`, `telat-per-orang`, `makasih-reaksi`, `tiga-alat-sekaligus`, so v3 reports still compare. A plain list still works, as a fixed set for every version.

Two exam briefs measure work the next spec builds: `notulen-jadi-tugas` (Tasks from the action items of Minutes) and `colek-h-1` (a Nudge for the Assignee the day before a due date, which follows the date when it moves). Today a model passes them only by doing that work by hand.

A brief or holdout that does not exist, a missing weight, or a fixture without an area stops the run before it starts. Per profile, an area scores the mean of its exam briefs' scores, held-out ones included, and the total is the mean of the areas with a brief in the run, weighted, the weights renormalised over them: a run of the recall briefs alone scores recall alone. `report.md` opens with `Rapor v<version>: <total>` for each profile, and has a table per area with its weight, score, the number of its briefs that ran, and the score of its held-out briefs alone; `report.json` holds the same under `summary.profiles[].rapor`. An area that scores well above its holdout score was fitted to its briefs.

**The held-out rule.** A holdout brief never tunes anything the bot reads: `packages/skills/src/workspace/vocabulary.ts`, the persona, a tool description, or a playbook. Read why it fails, then make the fix against another brief that fails the same way, adding one if none does. A holdout brief that has been used to tune is no holdout any more: add it to `holdout.spent` and bump `version`, which draws a new set without it. The current version's holdouts are what `loadExam().holdout` returns; the report's per-area table shows their score.

## The lived-in exam

The Rapor's briefs each seed a tiny world: a few kept files and Tasks. The lived-in exam (#252) asks what a team asks after months of use, against one shared Workspace, in sessions of two to five turns. It is a separate exam with its own scorecard and score, so the Rapor's 30 briefs and its score stay as they were.

- **The corpus** (`lived-in/story.ts`, `lived-in/corpus.ts`): one guild from 1 July to 13 October 2026, a small team building a podcast app in #general (the brief's channel, channel-1 named `general`), #audio-engine, #mobile and #marketing. `story.ts` holds by hand everything the sessions ask about: 24 Minutes, 14 story days, 10 Decisions (two of them replace an earlier decision), 11 Notes (word for word, slang and typos as people write), 10 Documents, 44 Tasks of every status (seven late on the clock), and a git history of 20 pull requests (merged, closed without merging, open), 8 issues and 20 commits across `gema/*`. `corpus.ts` renders it in the bot's own formats: Daily logs as `dailyLog.ts` keeps them, in monthly folders, Minutes as `minutes.ts` keeps them, Decisions, Notes and Documents with the head `addKeywords` writes, Tasks through `taskFile.ts`; then it fills every other working day from each channel's routine topics, which share the story's words on purpose (normalization, export, latency, noise, release). 370 files, 326 of them kept material; the same on every build, with no network and no model. `bun apps/agent/eval/lived-in/corpus.ts <folder>` writes it out to read.
- **The sessions** (`lived-in/sessions/`): 19 briefs in the usual format whose `facts.yaml` says `corpus: lived-in`, 14 in Indonesian and 5 in English, all five areas. They cover "was it discussed and is it done?" across Minutes, Tasks and pull requests; a Decision replaced by a newer one; a false premise ("kapan kita mutusin pindah ke Supabase?", never decided); asked in one language, kept in the other; who owns what and by when; late tasks; follow-ups that depend on the answer before; an answer only a Document holds; the same word on another topic.
- **Gold sources**: a turn may name `gold`, the sources a good answer rests on: a kept file as `#<channel>/<path below its folder>`, a Task as `task:<a phrase of its title>`, a pull request, issue or commit by its URL; a list in place of one names sources that stand in for each other, such as a Minutes and the same day's Daily log. `search` is the recall call a model would make for the turn. Neither is a check: they score retrieval, live (the Retrieval section of `report.md`) and in CI.
- **Retrieval in CI**: `apps/agent/test/lived-in-recall.test.ts` seeds the corpus and runs the `recall` tool once for every turn with a `search`, through the real bot with the scripted model, and scores each result against the turn's gold. It prints each question with its gold ranks and pins the scores as a floor: recall@5 0.90 and MRR 0.97 over 32 questions when it was written. A change may raise them, never lower them. A second scenario re-renders a Daily log through `dailyLog.ts` and parses every Minutes and Task, so the corpus stays in the formats the bot writes.
- **Scoring**: `lived-in/scorecard.yaml`, named `Lived-in`: recall 50, tasks 20, capture, group and loop 10 each, six sessions drawn out as the Rapor's are. `report.md` opens with `Lived-in v<version>: <score>`.
- **Running it live**: `EVAL_LIVE=1 EVAL_EXAM=lived-in EVAL_PROFILES=… EVAL_JUDGE_PROVIDER=… bun run eval:assistant`, with the judge env as for any live run (or `EVAL_JUDGE_PROVIDER=offline`, then `offline-judge.ts` as usual).
- **A new session** needs its folder under `lived-in/sessions/` with `corpus: lived-in`, its name in `lived-in/scorecard.yaml` (bump `version`), and gold and a search on the turns that look something up. A recording is optional: `eval-lived-in-dry-run.test.ts` dry-runs `loudness-dibahas-selesai` and `supabase-tidak-pernah-diputuskan`, recorded under `recorded/lived-in/`; their names are required in `eval-assistant-checks.test.ts`. A change to the story or the routine topics changes what every session sees: run the recall benchmark and re-record.

## Fixtures

### Issue drafts: `briefs/`

One folder per brief:

- `brief.md`: the author's message.
- `answers.md`: the author's reply to round 1. The harness posts it, then "draft now" when no draft is up. Nobody simulates the author beyond that.
- `facts.yaml`: `language` (`en` or `id`), `cases` (edge cases, from `one-line`, `vague`, `duplicate`, `ambiguous-repository`, `mixed-language`, `screenshot`), `mustCover`, `knownGaps`, `repoFacts` (facts true at the pinned commit), and `alsoOpen` (stub repositories with only a README, opened beside pachiware for an ambiguous brief).
- Any `.png`, `.jpg`, `.webp` or `.gif` is attached to the brief. A `screenshot` fixture must have one, and its facts should need the image to be covered.

The briefs are rewritten from this repository's history: the spec tickets #33 to #49, earlier decision issues, and PROGRESS phases. The real issue supplies the reference facts. When a draft fails in Discord, add its brief here.

Reference facts describe the repository at the pinned commit. Moving the pin means checking every `repoFacts` line and re-recording `recorded/`.

### Daily behaviours: `assistant/`

One folder per brief:

- `brief.md`: the first message, sent with a mention in the channel.
- `follow-ups.md`: later messages, one per block split on a `---` line, sent in the thread the bot opened. Optional. Alice sends each, unless the block begins with `@<member>:` (`@Bob:`, `@Dewi Anggraini:`), the display name of Alice, Bob or one of `members`: then that member does. A block beginning `@<a>+@<b>:` holds one line per member named, sent at once as a burst, the first line by the first member.
- `facts.yaml`: `language`; `area`, the Rapor area the brief scores in (`capture`, `recall`, `tasks`, `group` or `loop`); `clock`, the instant the conversation starts at (every brief uses a Wednesday 09:00 in Asia/Jakarta, so "Friday", "tomorrow" and "in two hours" have one answer); optional `settings` (guild `timezone`, `language`), `grants` (guild permissions the author holds, such as `ManageGuild`), `members` (guild members besides Alice and Bob: `id`, display `name`, optional `username`), `seed.messages` (the channel's talk before the brief, oldest first, posted as history the bot never saw arrive: `author`, the display name of Alice, Bob or one of `members`; `text`; `at`, an ISO time or a number of minutes before `clock`, never after it; an optional `channel` name for another channel of the guild; an optional `replyTo`, the index of an earlier message in the same channel), `seed.tasks` (task files written before the brief; their ids are `00000001-…`, `00000002-…` in order; a `channel` name files one in that other channel of the guild instead), `seed.files` (Workspace files written before the brief: `path` below the channel's folder, such as `minutes/2026-10-07-launch-sync.md`, `content`, and an optional `channel` as for tasks), `seed.hidden` (channels the guild's @everyone cannot view, so they are no Public channel; the author still can), `seed.git` (a GitHub account opening `repos`, holding `pullRequests`, `issues` and `commits` its search and commit list serve), `seed.home` (the display name of the brief's channel), `corpus` (a shared corpus seeded before the brief's own seed, `lived-in`; see "The lived-in exam"), and `attachments` (`name` plus `pdf` lines, attached to the brief as a real one-page PDF); `mustCover`; `turns`, one entry per message with what is expected after it (`ambiguous`, `tasks` with optional `channel` and `notes`, `memory.channel` / `memory.guild` with `has` and `lacks`, `files`, `reminders`, `kept`, `cites` (indexes into `seed.messages`), `replyContains`, `replyLacks`, `taskList`, `quiet: true` for a message not for the bot to answer, such as one aimed at someone else or a thanks, and `reaction`, the emoji of which the bot must leave one; a quiet turn is graded by code alone, the judge is asked nothing about it; `tasksInclude`, tasks that must exist among any others; and `gold` and `search` for retrieval, see "The lived-in exam"); and `then`: `dailyLog`, a day (`2026-10-13`) whose Daily log of the brief's channel the bot writes from the seeded talk with the profile under test before the brief is sent, so what it wrote is in the recorded state from the first turn (a day without seeded talk in the brief's channel, in the place's zone, is refused, and a log not written fails the first turn); and `clock` with the Reminder `posts` expected after one scheduler tick there, after the conversation.

## Recorded dry runs

`recorded/*.json`, `recorded/assistant/*.json` and `recorded/lived-in/*.json` are outputs of a scripted model (`profile: { provider: "scripted", model: "dry run" }`) driven through the real bot by `apps/agent/test/eval-dry-run.test.ts`, `apps/agent/test/eval-assistant-dry-run.test.ts` and its siblings. The checks tests re-grade them on every `bun test`, so a change to a check, a fixture or the bot's own text shows up without a key. To re-record the daily-behaviour runs after such a change: `EVAL_RECORD=1 bun test apps/agent/test/eval-assistant-dry-run.test.ts` (and `eval-rapor-dry-run.test.ts`, `eval-lived-in-dry-run.test.ts` for theirs).

## Calibrating the judge by hand

The judge is trusted only once it agrees with a person (issue #49). Until then the rubric versions stay below 1 (`RUBRIC_VERSION` in `judge.ts` and `ASSISTANT_RUBRIC_VERSION` in `assistantJudge.ts`).

### Grading the judge by hand

For a daily-behaviour run, `hand-grade.ts` does the sampling and the counting (#252). The run is a folder whose trials the judge graded: a run judged over HTTP, or the `rejudged-<rubric>/` folder offline judging wrote.

1. `bun apps/agent/eval/hand-grade.ts sample apps/agent/eval/results/<run> [count]` writes `hand-grades.yaml` in that folder: `count` items (24 by default, never fewer than 20), each one question the judge answered (`fact <n>`, or `behaviour` or `supported` with its turn), word for word with everything the judge saw, the rubric it followed at the top, and no verdict. The sample is the same for the same run: spread over the briefs, alternating items the judge said no to with ones it said yes to while both last, so a judge that says yes to everything cannot agree by default. Items the judge left unknown are not sampled.
2. Grade each item yourself from what it shows: `human: yes` or `human: no`, and a `note` on anything unclear. Leave `human` empty to skip one.
3. `bun apps/agent/eval/hand-grade.ts agree apps/agent/eval/results/<run>` prints, and keeps as `hand-agreement.md`, the share of graded items where the judge's verdict equals yours, overall and per criterion, every disagreement with your note, how many items are left, and whether the freeze bar below is met.
4. `bun apps/agent/eval/hand-grade.ts keep apps/agent/eval/results/<run>` adds the graded items to `calibration/<rubric>.yaml`, once each, so `rejudge.ts` compares every later regrade of the run with them (step 4 below).

The steps below are the same work done by hand, for issue-draft runs too.

1. Run the live eval with one profile and `EVAL_TRIALS=1`.
2. Take at least 20 items across different briefs from `results/<run>/trials/*.json`. For issue drafts each file holds the drafts (`result.drafts`), the questions (`result.questions`), and the judge's verdicts with reasoning (`result.judged`); for daily behaviours it holds the turns with their replies and recorded state (`result.turns`) and the verdicts per fact and per turn (`result.judged`).
3. Grade each criterion yourself before reading the judge's verdict, `yes` or `no`, and keep it as an item of `calibration/<rubric version>.yaml`: `{run, trial, turn, criterion, human, note}`, where `run` is the folder under `results/`, `trial` a file under its `trials/` without `.json`, and `criterion` is `fact <n>` (the nth must-cover fact) or `question <n>` without a turn, `behaviour` or `supported` with its `turn`, or `invented` with the draft's number as `turn` (the file's header shows two). Use only what the judge sees: the brief, the answers and `facts.yaml`, or the conversation, the recorded state and `facts.yaml`. A criterion that material cannot settle is left out. Both rubrics are at 0.1, so `0.1.yaml` holds the grades of both; each item names its run.
4. Grade the run again without running the bot: `bun apps/agent/eval/rejudge.ts apps/agent/eval/results/<run>` writes `rejudged-<version>/` with the same trials and a new report, using the rubric the run's `report.json` names (`kind`); a daily-behaviour trial's code checks are run again from its recorded output against the facts as they are now, so a fixed fixture regrades too, and prints how often the judge agrees with your grades for that version: the share of items where its verdict equals yours (an `unknown` never does), overall and per criterion, every disagreement with your note, and every item naming a trial or criterion the run does not have. The same text is kept as `agreement.md`.
5. For every disagreement, decide whether the rubric text was unclear (change the system prompt or the criterion's question in `judge.ts` or `assistantJudge.ts`), the reference facts were wrong or vague (fix `facts.yaml`), or the judge is simply wrong in a way you accept (note it as a known limit below). Bump the rubric version on every rubric change, so reports at different versions are never compared, copy your grades to the new version's file, and rejudge.
6. The rubric freezes at 1.0 when the judge agrees with you on at least 90% of at least 20 items; the agreement text says when the bar is met. Set its version to `1.0`, and record under Frozen rubric versions the date, the run graded, the number of items compared and agreed, and the known limits below. From then on any change to the rubric text or the pass rule is a new version, and only reports at the same version are compared.

One entry per rubric frozen at 1.0: the rubric (issue drafts or daily behaviours), the date, the run graded, and the items compared and agreed (at least 20, at least 90% agreed).
